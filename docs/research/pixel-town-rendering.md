# Rendering code-authored pixel towns

Date: 2026-09-27. Research for [Compare rendering methods for code-authored animated pixel towns](https://github.com/BriceChivu/Edenia/issues/346), within [Build and deploy Edenia's internal pixel-art town trial](https://github.com/BriceChivu/Edenia/issues/344).

## Recommendation and evidence boundary

Prototype a **small, dependency-free Canvas 2D compositor with cached static artwork and a few code-generated sprite patches**. Author the artwork as deterministic pixel sprites, palette roles, and stage composition data. Generate fallback stills and reusable animation frames at build time. At runtime, compose the selected stage and lighting once, then update only the sparse moving layer. Keep CSS responsible for the surrounding layout.

The owner selected **classic overhead pixel art close to Pokémon's visual language**, with every earned landmark visible on phones **without dragging or zooming**. Reinterpret the recognizable Edenia landmarks in that overhead view; do not preserve the current oblique camera. These constraints were confirmed during research and are recorded in the map.

This is an engineering recommendation, **not a measured performance result or visual approval**. Canvas caching/layering is documented; whether runtime composition or build-generated static plates give Edenia the better loading/maintenance tradeoff needs the representative-art benchmark below. Do not begin by building a game engine, a continuous full-scene renderer, WebGL shaders, or a worker protocol.

No product code, prototype, browser benchmark, hosted setting, or deployment was changed during this research. The measurements below concern existing local files only. The source snapshot is [`a9c14ef5f501bcae97fbb6bce5c68f3297e1e040`](https://github.com/BriceChivu/Edenia/tree/a9c14ef5f501bcae97fbb6bce5c68f3297e1e040); recheck integration against the implementation base. Pip's scheduling precedent is supplied by the ticket; Pip is absent from this snapshot and was not independently verified here.

## Method comparison

The cost/maintenance judgments in this table are hypotheses for Edenia, not universal renderer rankings.

| Approach | Why it fits | Cost or limitation | Recommendation |
| --- | --- | --- | --- |
| Runtime Canvas 2D; draw static layers once, cache sprites and lit composition | Small scene descriptions; direct palette control; no per-object DOM; one authoring language | First composition and palette changes occupy the main thread; several backing surfaces consume memory | Preferred compositor; measure initial work and bound caches |
| Code-generated static plates and small sprite atlases | Move detailed drawing into the build; stills work without a running animation renderer; simple frame selection | Download/decode cost; stage × time × size variants can multiply; full-scene animation atlases duplicate static pixels | Generate reusable frames and fallback stills; compare pre-baked plates against runtime static composition |
| Static image plus a few CSS sprite layers | Cheap prototype for very few moving patches; simple styling | Sprite `background-position` and SVG paint changes are not automatically compositor-only; many elements/layers complicate clipping and occlusion | Useful comparison, especially for onboarding; avoid hundreds of DOM pixel elements |
| SVG scene with CSS animation | Code-authored geometry and reusable symbols; easy element inspection | Crisp raster grid must still be designed; per-pixel rectangles/filter effects create complexity; scaling paths is not pixel-art authoring | Possible build-time authoring source; not the first live renderer |
| WebGL | Batched sprites and programmable palette effects | Context-loss/resource lifecycle, texture limits, shaders and fallback work; no demonstrated need for sparse decorative motion | Reconsider only if measured Canvas composition fails after simpler reductions |

Mozilla recommends pre-rendering repeated objects, integer drawing coordinates, separating static and moving layers, and avoiding repeated scaling/shadow work. An offscreen cache can be an ordinary detached canvas; a worker is not required. `alpha: false` is appropriate only when that surface is fully opaque. [Mozilla Canvas optimization guide](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)

Google's browser guidance favors `transform` and `opacity` when they avoid layout/paint, while requiring actual pipeline inspection. It does not establish that every CSS sprite animation is cheaper than Canvas. [Chrome animation guide](https://web.dev/articles/animations-guide) WebGL additionally has explicit resource and context-loss considerations. [Mozilla WebGL guidance](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)

## Art production and rendering proposal

Beyond the owner's overhead-view and full-visibility constraints, these are proposals to test in the visual prototype.

1. **One reusable art vocabulary.** Define pixel patterns/sprites for stone rims, roofs, windows, foliage, dock, water edge, and landmarks; compose explicit stage definitions from them. Use stable object IDs and seeded texture variation so the same house does not redraw differently at every stage or refresh. Avoid random decorative noise as a substitute for authored shading.
2. **One source, two execution times.** A pure scene painter accepts stage, composition, palette and fixed animation phase. Use it in the authoring preview and build generator; emit deterministic stills/contact sheets and a small animation atlas. Start by painting the selected static scene into a cache at mount or stage/light change. If that startup work misses budget, pre-bake the costly static plates from the same source. PNG is a simple lossless baseline; compare lossless WebP by decoded pixel equality and actual bytes, not extension alone.
3. **Two active surfaces, not twelve scenes.** Keep an opaque static base and a transparent moving overlay, with at most the current scene and one transition target cached. For overlapping foregrounds, either precompose the animation patches including their occlusion or add one justified foreground layer. Start by clearing/redrawing the small overlay at low cadence; add dirty rectangles only if measurement warrants the bookkeeping. Compare one opaque composed canvas if the second layer's compositing cost is worse.
4. **Small authored motion.** Try 2–4 frame grass clusters at roughly 2–4 frame changes/second and a few water glints/reflection strips at up to 6–8. Stagger phases deterministically, hold still between changes, and keep roofs/islands fixed. Those rates are hypotheses, not requirements. Bake pixel shadows, reflected colors and window glow; avoid per-frame blur, full-scene pixel readback, real-time ray tracing, and physics.
5. **Beautiful still state first.** Review an early stage and stage 12 at midday, 18:30 and night before adding movement. Night should retain readable silhouettes and reflected window light rather than merely darkening everything. Retain DOM stage/progress text; decorative layers need no pointer listeners or keyboard targets. Keep timeline/level controls separate from the art.

Canvas supports drawing image subregions, so one small atlas can supply patches. It also has fallback-content requirements; a sibling still image is the robust visible fallback when a supported canvas fails at runtime, because nested canvas fallback is not normally displayed in that case. [HTML Canvas standard](https://html.spec.whatwg.org/multipage/canvas.html)

## Pixel sizing and composition

Compare approximately **384 × 216** and **512 × 288** authoring grids, then choose based on the full stage's readable detail at phone size. These are experiment inputs, not final dimensions. A 384 × 216 RGBA8 surface is 331,776 bytes; a 512 × 288 surface is 589,824 bytes by `width × height × 4`. Those calculations exclude browser copies, decoded images, GPU surfaces and overhead; they are not process-memory estimates.

Draw at integer art coordinates; disable Canvas image smoothing when scaling sprites. Keep the logical art resolution independent of display DPR instead of multiplying every cached surface by `devicePixelRatio`. Set display scaling separately and use `image-rendering: pixelated`. Canvas smoothing and CSS scaling are separate stages. [Canvas image smoothing](https://html.spec.whatwg.org/multipage/canvas.html#image-smoothing), [Mozilla pixel-art guide](https://developer.mozilla.org/en-US/docs/Games/Techniques/Crisp_pixel_art_look)

Do not promise perfect pixel equality at arbitrary sizes: the CSS specification permits smoothing for non-integer `pixelated` scaling, and fractional device ratios/zoom can create uneven pixels. Prefer integer scaling where it fits, snapped scene origins and modest padding; accept tested fractional scaling where necessary. Test browser zoom and DPR 1/2/3, not only screenshots at one desktop size. [CSS Images scaling specification](https://drafts.csswg.org/css-images-3/#the-image-rendering)

Use shared world coordinates but explicit desktop/phone framing. The phone layout must show all earned islands and the volcano without dragging or zooming. If merely shrinking the full scene makes details too small, author a compact overhead arrangement retaining landmark relationships; do not hide an earned milestone with `cover`. Let water fill surplus space. Reserve the viewport's dimensions before assets decode. Onboarding needs only its visible selected stage alive; other samples can remain stills. Do not attach the existing image zoom/pan handlers to experimental art; preserve public controls.

## Local clock and lifecycle

`Date.prototype.getHours()` uses local time. Derive fractional minutes from the device clock, not UTC, study-day history, IP location or a timezone service. Keep 18:00–19:00 inside the warm sunset phase; exact dawn/day/dusk/night stops require visual approval. [ECMAScript local-hour definition](https://tc39.es/ecma262/multipage/numbers-and-dates.html#sec-date.prototype.gethours)

Suggested implementation: interpolate palette roles (water, roof light/shadow, foliage, sky and emissive windows), quantize to an acceptable minute-scale step, and refresh static caches only when the resulting palette changes. Read wall-clock time on mount, visibility return and each scheduled light update so sleep/timezone changes recover naturally. Use monotonic elapsed time only for sprite phase. Do not animate lighting at display refresh. A frozen scene must still have the selected time-of-day palette.

`requestAnimationFrame` is a one-shot display-synchronized callback, commonly paused in hidden tabs; continually requesting it and skipping most draws still executes callbacks at the display's refresh rate. Prefer one deadline timer for the next actual sprite change followed by one rAF to paint, while measuring its real scheduling behavior. Cancel both when inactive and skip missed frames after resume. [Mozilla rAF documentation](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)

Combine document visibility, viewport intersection and the component's own shown/hidden state. Intersection observation alone does not establish that an opacity-hidden onboarding scene is active. Explicitly stop animation, light timers and pending work when hidden/offscreen; recompute once when visible. Disconnect observers/listeners and release cache references on disposal; late decode completions must not revive a disposed scene. [Page visibility](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API), [Intersection Observer](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API)

Honor reduced motion at mount and when it changes: no ambient animation loop; retain the lit still. Keep a graceful still mode if Canvas, decoding or setup fails. OffscreenCanvas can move work into workers, but support alone is not a reason to add it; introduce it only after a trace identifies irreducible main-thread work. [Reduced-motion preference](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion), [OffscreenCanvas](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas)

The accessibility decision also needs an explicit stop mechanism for ongoing nonessential motion: WCAG's criterion covers automatically moving content lasting over five seconds beside other content. A settings control outside the artwork preserves noninteractive scenery; alternatively the motion can stop by itself. Reduced-motion support should not be assumed to resolve that whole decision. [W3C Pause, Stop, Hide explanation](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)

## Public-route isolation

The existing build bundles one app output with code splitting absent. **A conditional `import()` is insufficient on its own:** esbuild documents that without splitting the imported code stays in the same bundle. [Current build](https://github.com/BriceChivu/Edenia/blob/a9c14ef5f501bcae97fbb6bce5c68f3297e1e040/scripts/build-site.mjs#L94-L113), [esbuild splitting documentation](https://esbuild.github.io/api/#splitting)

Prefer a separately built, versioned experiment entry and stylesheet, loaded only after a central art selector allows the internal route. Verify the generated public bundle contains no scene data or renderer; verify no experiment preload, CSS import, image `src`, worker or atlas request appears on `/`. Preserve public images and selectors. Sharing a deployment directory is acceptable; downloading the experimental renderer to every visitor is not.

Within the internal route, avoid eagerly downloading all stages/times and avoid old-image preloading once the new town mounts. Shared static HTML currently references old images before application code runs, so measure those legacy requests honestly; any bootstrap change to suppress them must separately demonstrate unchanged public behavior. Keep the art selector independent of authentication/profile lifecycle. Authentication retirement belongs to its own ticket.

## Small benchmark to settle the remaining renderer choice

Use the **same authored early and full-stage scenes** for three variants: static-only new still; cached Canvas with sparse overlay; build-generated static plate/atlas with the same motion. A tiny CSS-patch comparison is worthwhile only if it depicts the same pixels and motion. There is no useful comparison between a polished static town and an unrelated synthetic bouncing square.

1. Fix stage, viewport, palette/time, animation seed and learner fixture. Compare current artwork, new static mode and new animation using the same build, feed size and video interactions. Run at least five alternating paired trials with cold and warm cache recorded separately; retain raw traces and medians/ranges.
2. Include desktop Chrome, real Safari/iPhone and a representative modest Android phone. CPU/network throttling helps reproduce stress but cannot establish mobile heat, power or Safari behavior. Test 30 seconds visible idle, feed scrolling, opening/playing video, stage history, onboarding changes, then hidden tab/offscreen and resume. Repeat stage/time changes to expose cache growth.
3. Record renderer/asset transferred bytes, first useful art time, maximum synchronous initialization task, per-update duration, main-thread scripting/paint/compositing, frame drops, interaction latency and retained surface count. Instrument callback/draw counts, not only apparent FPS. Performance marks alone omit later raster/compositor work. Use browser traces; feature-detect Event Timing/long-animation-frame APIs and never interpret absent support as zero cost. [Chrome Performance tooling](https://developer.chrome.com/docs/devtools/performance/reference/), [Event Timing](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceEventTiming), [long animation frames](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceLongAnimationFrameTiming)
4. **Proposed starting hypotheses, to ratify in the performance ticket:** no artwork-caused task over 50 ms; p95 animation update below 2 ms on the chosen modest phone; at most 8 draws/second for ambient motion; no continuing animation callbacks while hidden/offscreen or reduced-motion; no unbounded cache growth; no experimental requests/renderer bytes on the public route. Aim for no interaction-latency regression beyond paired-run noise; a repeatable increase above 10 ms is an investigation trigger, not an assertion of imperceptibility. An INP field score cannot be inferred from this small lab sample.
5. Budget first-view bytes and first-art time from the measured baseline and accepted artwork, not the 8.40 MiB directory total. Record decoded dimensions as well as compression. Review sustained CPU/energy behavior on hardware if motion stays continuously visible; a short trace cannot prove battery neutrality.

If a variant misses the contract, reduce motion patches/cadence and retain the beautiful still before adding infrastructure. If runtime initial painting is the only failure, pre-bake static plates. If transfer/decode dominates, keep shared code/tiles and cache only the current palette. The prototype resolves art quality and composition; the performance ticket resolves exact budgets and the final production choice. This research does not resolve either gate.
