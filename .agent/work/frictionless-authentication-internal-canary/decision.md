# Frictionless authentication internal canary decisions


This work replaces Edenia's visible Supabase-hosted Google redirect with Google Identity Services and completes a production-shaped email fallback, while keeping both Supabase and the supporting providers on their free plans. It ends with a private internal canary. It does not make accounts public or required.

The opaque Supabase project reference must not appear in an ordinary user's address bar, Google identity dialog, auth email, clickable link, or Edenia auth copy. The Free Supabase project URL remains public runtime configuration and can still be discovered by a technically sophisticated user in source or network tools. Hiding that infrastructure detail completely would require a proxy or paid custom domain and is not part of this work.

Google authentication uses Google Identity Services' official rendered button and `supabase.auth.signInWithIdToken`, not a custom imitation and not a Supabase OAuth redirect. The integration also offers Google One Tap and cancelable automatic sign-in. The manual Google button remains available in the optional final onboarding account step and in Settings. One Tap is never prompted during onboarding or the walkthrough. It becomes eligible only after `state.onboarding.setupCompleted` and `state.onboarding.walkthroughCompleted` are both true, the account is signed out, no walkthrough is active, and Google's own eligibility and cooldown rules allow it. Closing or ignoring the prompt never blocks study.

The first successful Google or email authentication creates the Edenia account without a separate registration screen. Supabase remains the session authority, sessions persist across browser restarts, and sign-out affects only the current browser. Explicit sign-out must cancel any active Google prompt and call `google.accounts.id.disableAutoSelect()` so the user is not immediately signed in again.

Every Google credential opportunity gets a fresh cryptographically random nonce. Only its SHA-256 digest is sent to Google, while the raw nonce is passed to Supabase with the ID token. Nonces and ID tokens remain in memory, are consumed once, and must never enter DOM attributes, URLs, storage, logs, analytics, or exception text.

Email remains a magic-link fallback rather than an OTP-entry screen. A branded Edenia email links to `https://www.edenia.study/auth/confirm/` with the Supabase `TokenHash` in the URL fragment. The analytics-free confirmation page captures the fragment in memory and removes it from visible history before loading unrelated application behavior. It does not exchange the token until the person deliberately selects **Continue to Edenia**, which prevents an email security scanner's page request from consuming the sign-in token. It handles invalid, expired, already-used, offline, retry, and success outcomes. Opening the link on another device signs in that device; the browser that requested it remains signed out and does not poll.

Magic-link requests use free Cloudflare Turnstile protection and retain conservative resend cooldown and rate-limit behavior. The client token path must be deployed and tested before CAPTCHA is enabled in Supabase. Enabling CAPTCHA must include a live check that Google ID-token and One Tap flows still work; if the project-wide setting unexpectedly requires an unplanned Google challenge, CAPTCHA is rolled back while the implementation is corrected rather than breaking Google sign-in.

Supabase's default sender is not a production path. Its two-project-emails-per-hour limit counts messages, not distinct users, so it can support at most two magic-link messages in an hour even when the recipients differ. Google sign-ins do not consume that quota. The production-shaped fallback uses Resend Free custom SMTP. Auth and reminders share the already verified neutral `mail.edenia.study` sending domain, with separate sender identities such as `accounts@mail.edenia.study` and `reminders@mail.edenia.study`. The accepted Free-plan ceiling is currently 3,000 messages per month, 100 per day, and one verified domain; auth and reminder traffic share that quota and sending reputation.

Authentication establishes the account identity but must not upload, replace, merge, clear, or otherwise modify the full browser-local study document. Existing separately gated reminder-preference behavior and the bounded reminder-eligibility snapshot remain unchanged; this work must not widen either payload. The rejected sentence `Your study progress stays in this browser. Signing in won’t upload or replace it.` must not be added to onboarding. Existing Settings copy about local progress can remain.

PostHog uses the normalized Supabase UUID as `distinct_id`, merges the current anonymous history into that identity on first sign-in, and stores the actual normalized email plus the authentication provider/method as searchable person properties. Email, Google subject, nonce, and tokens must never become `distinct_id`. Logout and account switching reset PostHog before any next user is identified. The accepted shared-device limitation is that pre-login anonymous events in the same browser can become associated with the person who signs in.

Supabase automatic identity linking is the intended same-email behavior. A verified address used through email and Google must resolve to the same Supabase UUID and therefore the same PostHog person. This work adds no manual identity-linking or email-change UI. The internal canary must prove UUID continuity in both practical sign-in sequences before the behavior is considered ready.

The complete implementation remains behind `EDENIA_ACCOUNT_FEATURES_ROLLOUT=internal` and `?internal_test=1`. The ordinary public/accountless route remains unchanged. Public account enablement, consent-screen publication and legal-page work, account deletion including PostHog deletion, email changes, manual identity management, and sign-out-everywhere are separate future tasks.
